=== 2. Concept Explanation (20 minutes)

==== Concept 1 — The Three Layers of a Problem (10 minutes)

Every problem situation has three layers.

----
Surface
  │
  ▼
┌─────────────────────────────────────────────────┐
│  Symptom                                         │
│  What's observable. Where the pain is felt.      │
│  "Users are churning"                            │
│  "Team members miss tasks"                       │
│  "Data is wrong"                                 │
└─────────────────────────────────────────────────┘
  │ Why?
  ▼
┌─────────────────────────────────────────────────┐
│  Problem                                         │
│  The direct cause of the symptom.                │
│  "Onboarding is too long"                        │
│  "No notification after assignment"              │
│  "No validation in the input screen"             │
└─────────────────────────────────────────────────┘
  │ Why?
  ▼
┌─────────────────────────────────────────────────┐
│  Root Cause                                      │
│  The deeper cause generating the problem.        │
│  "No value demonstration for new users"          │
│  "Assignment workflow happens outside system"    │
│  "No owner for data entry"                       │
└─────────────────────────────────────────────────┘
----

Why does the distinction matter?

----
Fixing at symptom layer:
  Painkiller → Symptom temporarily disappears → Problem remains, symptom recurs

Fixing at problem layer:
  Add notification → This problem is solved → Root cause remains, other problems emerge

Fixing at root cause layer:
  Bring assignment workflow fully into system → Multiple symptoms disappear at once
----

But this doesn't mean you always have to dig to the root cause. _Which layer to address is a conscious choice_. It's okay to decide to fix the symptom layer for a demo next month — as long as you know that is the decision you're making.

'''

_Problem Framing — How you frame it changes the solution_

How you frame the same phenomenon changes the shape of the Problem Space.

----
Phenomenon: "Team members miss tasks"

Frame A (seen as a notification problem):
  → Strengthen notification system
  → Technical solution emerges

Frame B (seen as a communication problem):
  → Redesign assignment process
  → Organizational/process solution emerges

Frame C (seen as a visibility problem):
  → Let team lead see team members' current tasks
  → Dashboard solution emerges

Frame D (seen as an accountability problem):
  → Assignment acknowledgement feature
  → Different kind of technical solution emerges
----

Which frame is "right" is not currently known. But _the most dangerous thing is having only one frame_. Recognizing that multiple frames are possible is the first practice.

'''

==== Concept 2 — Domain Model vs Design Model (Fairbanks) (10 minutes)

Fairbanks distinguishes three models surrounding software.

----
Domain Model  ←── Belongs to Problem Space
     │
     │  (this is the Bridge)
     ▼
Design Model  ←── Starting point of Solution Space
     │
     ▼
Code Model    ←── Actual implementation
----

_Domain Model — Real-world concepts_

The _real-world people, actions, rules, and states_ that this system deals with.

Domain Model elements in the TeamOrder case:

----
People (Actors):  Team lead / Team member / Client admin
Actions:          Task assignment / Task acknowledgement / Task completion / Urgent assignment
States:           Unassigned / Assigned / Acknowledged / In Progress / Done / Overdue
Rules:            Night shift urgents delivered immediately / Re-notify if unacknowledged / Deadline reminders
Objects:          Task / Team / Production line / Deadline
----

_Design Model — The structure of the software being built_

ERD, API design, system diagrams. From here, you're in the Solution Space.

The mistake most engineers make:

----
Requirement received
     │
     │ ← This is skipped
     ▼
Domain Model (understanding reality)
     │
     │ ← This is also skipped
     ▼
Design Model (ERD, API)  ← This is where they start
----

What happens when the Domain Model is skipped?

The design diverges from the real-world concepts. During development, "how do we handle this case?" questions keep repeating. Most of those questions belong in the Domain Model layer.

_The time to move to the Design Model is when the Domain Model has sufficiently stabilized._

How do you know? When the team is speaking the same domain vocabulary. When "task" and "to-do" aren't used interchangeably. When "Assigned" and "Acknowledged" are distinct.

=== 3. Fixed Case Exercise (30 minutes)


==== Small Group Share Guide

_Small Group Share (7 minutes)_

Pin or draw each group's Domain Model side by side on the board.

Facilitator guide:
----
Comparison Points
──────────────────
"How differently was State drawn across groups?"
  → State design varies the most.
    Teams that treated 'Assigned' and 'Acknowledged' as the same vs different.
    This difference will completely change DB design and API design later.

"How many Rules were found?"
  → Did any teams include the night shift urgent rule?
    Teams that didn't — reflect on why it was left out.

"How different is the Domain Model from the current design (if any)?"
  → Large gaps are future rework points.
----

=== 5. Debrief (10 minutes)

_Facilitator guide — anticipated resistance and responses_

----
"The symptom/problem/root cause boundary feels fuzzy."
────────────────────────────────────────────────────────
True. This boundary genuinely shifts with perspective.
'No notification after assignment' could be a symptom
or a problem depending on who you ask.
What matters is not "exact classification" —
it's that the team collectively recognizes
"which layer are we trying to fix."

"Do we always need to draw a Domain Model?
 Even for a small feature?"
────────────────────────────────────────
You don't need to pull out the tool every time.
The goal is not a 'Domain Model document' —
it's that 'domain vocabulary is aligned within the team.'
Naturally asking in Slack, "wait, 'Assigned' and 'Acknowledged'
are different things, right?" — that is also Domain Model work.

"Isn't it always better to fix the root cause?"
──────────────────────────────────────────────────
True. This is also the topic of Sessions 5 and 7.
With one month to demo, fixing the problem layer may be realistic.
What matters — is knowing that it is a choice.
"We are currently fixing the symptom.
 The root cause comes in Q2." — as a decision.
