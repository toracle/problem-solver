* ★ In business research, emphasize that the goal is reading Trade-offs, not a feature list. Make participants ask "what did this service sacrifice?"

=== 2. Concept Explanation (20 minutes)

==== Concept 1 — Analogical Reasoning (10 minutes)

One of the things Pólya emphasized most in _How to Solve It_.

[quote]
____
_"Do you know a related problem?"_
____

There is no need to treat a problem as if you're seeing it for the first time. If the _structure_ of this problem resembles a known problem in another domain, you can bring in the logic of that solution.

Three steps of analogical reasoning:

----
Step 1: Extract the structure
  What is the core structure of this problem?
  (Abstract the actors, actions, relationships, constraints)

Step 2: Search for analogous problems
  Is there a problem in another domain that resembles this structure?

Step 3: Import the principle
  Apply the solution principle of the analogous problem to this problem
  (the principle, not the solution itself)
----

_TeamOrder case application example:_

----
Step 1 — Extract the structure:
  "Delivering messages to multiple recipients,
   where recipients' states (online/offline/sleep) are uncertain,
   and message urgency varies"

Step 2 — Search for analogous problems:
  • Hospital ER triage — sequencing by patient urgency
  • Air traffic control — priority communication among multiple aircraft
  • Email spam filter — sorting by importance
  • TCP retransmission — retry mechanism when packet not acknowledged
  • Twitter notification batching — critical notifications immediately,
    rest bundled

Step 3 — Import the principle:
  TCP retransmission principle:
    "Retransmit if no delivery confirmation received"
    → Re-notify if team member notification acknowledgement is absent
  Triage principle:
    "Use different channels based on urgency"
    → Night-shift urgents via separate channel (SMS/call),
      regular via app push
----

An important caveat: _This is not copying the solution._ It is importing the principle. Not using TCP as-is, but bringing the logical structure of "retry if no acknowledgement."

==== Concept 2 — Reduction (5 minutes)

Reduction is mapping a complex problem onto a known _problem type_.

----
"What kind of problem is this, fundamentally?"
----

Commonly used problem-type vocabulary:

[cols="1,1,1", options="header"]
|===
| Problem type | Core structure | Typical examples
| _Matching problem_ | Optimally connecting set A to set B | Courier-order, job-seeker-hiring
| _Trust problem_ | Building trust between strangers | Used goods marketplace, accommodation sharing
| _Cold Start problem_ | Recommendations with no initial data | New user, new product
| _Visibility problem_ | One side doesn't know the other's state | Team task status, logistics location
| _Rate Control problem_ | Requests exceed processing capacity | API throttling, notification fatigue
| _Consistency problem_ | Data diverges across multiple locations | Distributed systems, multi-device
|===


TeamOrder case: _A combination of Visibility problem + Rate Control problem_

The team lead doesn't know whether team members have seen their assignments (Visibility), and too many notifications get ignored (Rate Control).

Knowing these two problem types means — there are validated solution patterns for each type.

==== Concept 3 — Business Research: Reading Trade-offs (5 minutes)

When researching competing or similar services, simply listing features isn't very useful.

From Cunningham's perspective — other services already have _the results of exploring Essential Ambiguity through action_ embedded in their products.

What you should read is _the Trade-offs they chose_.

----
Business research question frame:

"What did this service prioritize above all else?"
"What did it sacrifice?"
"Why did they choose this approach?"
"What type of user/environment is it optimized for?"
"In what situations does this design fail?"
----

Example: Slack's notification design
* Top priority: Message delivery reliability + notification customization
* What was sacrificed: Simplicity (settings are too complex)
* Optimized environment: Desktop-centric knowledge workers
* Where it fails: Field workers, users who don't configure notifications

TeamOrder's users are field workers. This is where you can see why Slack's design doesn't work for them.

==== Small Group Share Guide

_Small Group Share (10 minutes)_

Facilitator guide:
----
Comparison Points
────────────────
"Did different teams find analogies from entirely different domains?"
  → The same problem can generate analogies from completely different domains.
    If one team found hospital triage and another found TCP retransmission,
    both are correct. And the principles extracted from each will differ.
    List those differences on the board.

"Where did things get stuck when importing the principle?"
  → Check: "Were they trying to copy the solution or import the principle?"
    The former usually ends with "it doesn't fit our situation."

"How did reading Trade-offs in business research
 differ from a simple feature comparison?"
  → Surface this question to help participants articulate
    the difference in research perspective.
----

=== 5. Debrief (10 minutes)

_Facilitator guide — anticipated resistance and responses_

----
"Finding analogies feels like it would take too long."
────────────────────────────────────────────────────
It does at first. But this is training.
After doing it a few times, you'll start to hear a problem
and automatically think "I've seen this structure somewhere."
That moment is one of the shifts from 3–4 years of experience
to 5–6 years.

"Can't analogies be wrong?"
────────────────────────────────────────────────────
Yes. Analogical reasoning can be wrong.
But discovering that "it was wrong" is also learning.
Finding that "unlike TCP, our problem can't force
acknowledgement" can lead to a deeper understanding
of the problem itself.

"Can't you only use analogies from domains you already know?
 How do you find them from unfamiliar domains?"
────────────────────────────────────────────────────────────
Two approaches.
First, search using problem-type vocabulary.
Terms like "Visibility problem solution" and
"notification fatigue pattern" as search queries.
Second, people with different experiences within a team
can surface different analogies. This is why teams with
diverse backgrounds have an advantage.
----
