=== 2. Concept Explanation (20 minutes)

==== Concept 1 — Three Sources of Ambiguity (8 minutes)

Weinberg explains that ambiguity in requirements comes from three different places.

_① Linguistic Ambiguity_
When the word itself carries no measurement standard.

----
"Fast response"          → How fast? 200ms? 2 seconds?
"Easy to use"            → For whom? In what situation?
"Secure"                 → From what threats? To what level?
"Better"                 → By what measure?
----

These words have a standard in the speaker's mind. But that standard wasn't transmitted.

_② Between-Interpreter Ambiguity_
When different people picture different things from the same word.

----
"Enhanced notifications"
  BizDev imagined:          Popup on client team lead's PC
  Backend developer:        Email / Slack webhook
  Frontend developer:       In-app badge, red dot
  User (team member):       Can't we just get a text?
----

Talking in the same language, but describing entirely different things. Everyone has experienced what happens when development starts in this state.

_③ Missing Context Ambiguity_
When there are unstated assumptions.

----
"It should work just like it does now"  → Do you know how it works now?
"Obviously that wouldn't be done"       → What's obvious?
"While keeping the existing approach"   → What is the existing approach?
"Build it quickly"                      → How quickly? What can be sacrificed?
----

These assumptions go unsaid by the speaker because they're too obvious to them. But they're unknowable to the listener.

==== Concept 2 — Functions / Attributes / Constraints Triangle (12 minutes)

Weinberg sees all requirements as actually composed of three different categories.

----
           Functions
           (what it does)
               △
              / \
             /   \
            /     \
           /       \
Attributes ─────── Constraints
(how it must do it)  (what cannot be touched)
----

[cols="1,1,1,1", options="header"]
|===
| Category | Definition | Typical expression | Common trap
| _Functions_ | Actions the system performs | "Process a payment," "send a notification," "assign a task" | Take note only of these and stop
| _Attributes_ | Quality criteria for those actions | "Under 200ms," "99.9% availability," "on mobile too" | These cause rework later
| _Constraints_ | Conditions the solution must respect | "PCI-DSS compliance," "budget of $200K," "cannot change existing DB" | Only discovered after design is done
|===


Why does this distinction matter?

_If only Functions are heard:_
"Send a notification" → Think any method will do
→ Implement via email
→ Later: "it needs to be real-time" (an Attribute) surfaces
→ Rework

_If Attributes are heard first:_
"In real-time, on all platforms, within 1 second" → Attributes determine Architecture
→ WebSocket considered from the start

_If Constraints are discovered late:_
Design is complete → "Oh, by the way, the client's network blocks WebSocket"
→ Full redesign

Conclusion: _Attributes and Constraints only surface if you actively draw them out._
Both BizDev and users naturally speak in Function language.
Engineers must extract them through questions.

==== Debrief Guide

=== 5. Debrief (10 minutes)

_Facilitator guide — anticipated resistance and responses_

----
"The boundary between Attributes and Functions is confusing"
────────────────────────────────────────────────────────────
That is normal. The boundary genuinely shifts depending on context.
"Real-time" can be an Attribute or a core Function depending on the situation.
What matters is not the classification itself, but whether
the team has the same understanding of that item.

"The Constraints column is hard to fill in"
────────────────────────────────────────────
Constraints are the hardest to surface.
The reason is that stakeholders don't say them because they're "obvious."
Next session (Session 3) covers the questioning techniques for drawing these out.

"Once FAC is all filled in, can we start development?"
────────────────────────────────────────────────────────
If all "?" become "confirmed," yes.
But some "?" may stay even after asking.
That's what Session 5 (living with ambiguity) covers.
For now, the goal is simply knowing what you don't know.

"Do we really have to do all this every time? It seems like it would take too long"
───────────────────────────────────────────────────────────────────────────────────
It takes time at first. But the goal is to use these tools
naturally within conversation.
The final goal is not "filling in a FAC table" —
it's "automatically checking these three things in your head."
----
