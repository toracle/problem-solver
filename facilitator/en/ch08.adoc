=== 2. Concept Explanation (15 minutes)

==== Concept 1 — Problem-Solution Fit (7 minutes)

What must be continuously checked before building the solution — and while building it:

_Is the problem I've defined actually connected to the solution I've built?_

----
Problem-Solution Fit check:

┌──────────────────────────────────────────────────┐
│ Problem definition (Problem Space exploration     │
│ results)                                         │
│                                                  │
│  - Who is suffering?                             │
│  - In what situation?                            │
│  - What workaround are they using now?           │
│  - What cost occurs if this isn't resolved?      │
│                                                  │
│           ↕  Does this correspond?               │
│                                                  │
│ Solution (Solution Space exploration results)    │
│                                                  │
│  - Whose pain does this feature alleviate?       │
│  - In what situation does it work?               │
│  - Does it replace the workaround?               │
│  - What remains unresolved?                      │
└──────────────────────────────────────────────────┘
----

The most common mismatch:

----
Problem: "Team members miss tasks and the line stops"
Solution: "Nice notification UI + read receipts + notification history page"

→ Do read receipts and a history page prevent line stoppages?
  The core of the problem (guaranteed delivery) is missing.
----

Three practical questions for the Fit check:

. *"If this feature didn't exist, what would users do?"*
   → If the workaround would remain intact, Fit hasn't been achieved.

. *"Could the problem still occur even with this feature?"*
   → If yes, the core has been missed.

. *"Is there anything not built that is needed to solve this problem?"*
   → If there is, decide: does it need to happen now, or can it wait?

==== Concept 2 — Pre-mortem: Reverse Simulation (8 minutes)

A technique proposed by Gary Klein.

Normal review: "Why will this solution succeed?"
Pre-mortem: "Assume this solution was adopted and failed 6 months later — what were the reasons?"

Why reverse is more effective:

----
Normal review                   Pre-mortem
───────────────────────────     ───────────────────────────────
Success bias develops            Imagining failure reduces bias
"It'll work out"                  "If it failed, why?"
Hard to find weaknesses          Weaknesses surface naturally
Psychologically hard to          Hypothetical failure creates
criticize in team setting        psychological safety
----

How to run a Pre-mortem:

----
1. "Assume this solution was actually deployed."
2. "Six months have passed."
3. "It failed. For what reasons?"
4. Each person writes 3+ reasons individually (2 minutes)
5. Small group share → extract top 3 most-cited failure reasons
6. Can those reasons be addressed preemptively?
----

_TeamOrder case Pre-mortem examples:_

----
"Reasons TeamOrder's notification feature failed after 6 months"

• Night-shift urgent SMS costs ran higher than expected — feature was turned off
• Team members were receiving too many notifications and started turning them off
• Background notification policy changed after an iOS update
• Team leads didn't know what to do with team members who hadn't confirmed,
  so they stopped using it
• The factory's firewall was blocking FCM (discovered later)
----

What can be addressed preemptively now:
* SMS costs → Set a monthly cap; let users set urgent flags themselves
* Notification fatigue → Rate Control logic (analogical reasoning from Session 6)
* Firewall → Confirm client network requirements as a Constraint (Session 2 FAC)

=== 5. Debrief (10 minutes)

_Anticipated difficulties and responses_

----
"I felt anxious that we were building too few features"
  → This is the core moment of learning. Use the TeamOrder outcome
    to directly show why "exactly what's needed" is a compliment.

"Worksheet B doesn't feel complete"
  → Completion is not the goal. What's sufficient is the trace
    showing how problem understanding deepened across 8 sessions.

"I'm not sure I can actually use the tools"
  → Have them remember just one thing.
    When you receive a requirement → pause just once → ask a question.
    The rest attaches naturally through experience.
----

_Facilitator guide — core convergence of this session_

----
Converge to a single message that runs through all 8 sessions.

"When you truly understand the problem, the solution actually becomes simpler."

This is the conclusion of the entire workshop.

Do you remember what you came up with in 30 seconds in Session 1?
If the solution then and the solution now are different,
ask where that difference came from.

It might be that identifying Attributes in Session 2's FAC
meant you didn't need to build unnecessary features.

It might be that deciding "fix the problem, not the symptom"
in Session 4's layer choice narrowed the scope.

It might be that resolving technical uncertainty through
Session 5's Spike meant you didn't spend two weeks
going in the wrong direction.

It might be that knowing "this doesn't need to be done now"
from Session 7's risk identification enabled focus for the demo.

All of this is the result of Problem Space exploration.
Because we spent more time understanding, we could build less,
more precisely, and deliver sooner.
